What is Broken Access Control?

Broken Access Control occurs when an application fails to properly enforce restrictions on what authenticated users are allowed to do. This enables attackers to access unauthorized functionality and data, acting outside their intended permissions. [VERIFY SOURCE] Access control enforces policy such that users cannot act outside of their intended permissions. When these controls fail or are improperly implemented, attackers can:

  • Access unauthorized data: View or modify other users' accounts, private information, or restricted resources
  • Perform privileged actions: Execute admin functions without proper authorization
  • Bypass authentication: Access protected resources without logging in
  • Elevate privileges: Gain higher-level permissions (admin, superuser)
  • Manipulate metadata: Modify access control tokens, cookies, or hidden fields
  • Exploit CORS misconfigurations: Access APIs from unauthorized origins

Why is it Critical?

Broken Access Control is the #1 vulnerability in the OWASP Top 10 (2021) and remains pervasive because:

  • It leads to unauthorized data exposure and privacy violations
  • Can result in complete account takeover
  • Often enables privilege escalation to administrative access
  • Difficult to detect with automated testing alone
  • Found in both legacy systems and modern applications
  • 94% of applications tested had some form of broken access control [VERIFY SOURCE]

Types of Access Control

  • Vertical Access Control: Different types of users have access to different application functions (admin vs. user)
  • Horizontal Access Control: Users have access to a subset of resources of the same type (User A's data vs. User B's data)
  • Context-Dependent Access Control: Access depends on the application state or workflow (can only cancel your own pending orders)

How Broken Access Control Works

The Vulnerable Pattern

Broken Access Control occurs when applications rely on client-side controls or fail to verify authorization on the server-side:

# VULNERABLE CODE - No authorization check
@app.route('/user/profile')
def get_profile():
    user_id = request.args.get('user_id')
    # DANGEROUS: No check if current user can access this user_id
    user = db.get_user(user_id)
    return render_template('profile.html', user=user)

The Attack

An attacker modifies the user_id parameter to access other users' profiles:

# Normal request (User ID 123):
GET /user/profile?user_id=123

# Attacker changes parameter:
GET /user/profile?user_id=456
# ✅ Access to User 456's profile without authorization!

# Try admin account:
GET /user/profile?user_id=1
# ✅ Potential admin account access!

Common Vulnerability Patterns

1. Insecure Direct Object References (IDOR)

Direct access to objects without authorization checks:

# VULNERABLE: Direct database access
@app.route('/document/')
def view_document(doc_id):
    document = Document.query.get(doc_id)  # No ownership check!
    return render_template('document.html', doc=document)

# Attack:
# /document/1 - Your document
# /document/2 - Someone else's document (accessible!)
# /document/100 - Try sequential IDs

2. Missing Function Level Access Control

Privileged functions accessible to regular users:

# VULNERABLE: Admin function with no role check
@app.route('/admin/delete_user')
def delete_user():
    user_id = request.args.get('user_id')
    User.query.filter_by(id=user_id).delete()  # No admin check!
    return "User deleted"

# Any authenticated user can call this endpoint!

3. Parameter Tampering

Manipulating request parameters to gain unauthorized access:

# Original request:
POST /update_profile
{
    "user_id": 123,
    "email": "user@example.com",
    "role": "user"
}

# Attacker modifies hidden parameters:
POST /update_profile
{
    "user_id": 123,
    "email": "user@example.com",
    "role": "admin"  # Privilege escalation!
}

4. JWT/Token Manipulation

Weak or improperly validated tokens:

# Vulnerable JWT payload:
{
    "user_id": 123,
    "role": "user",
    "admin": false
}

# Attacker modifies (if not properly signed):
{
    "user_id": 123,
    "role": "admin",
    "admin": true
}

5. Path Traversal in Access Control

Bypassing directory restrictions:

# Intended access:
GET /files/user123/document.pdf

# Attack with path traversal:
GET /files/user123/../user456/document.pdf
GET /files/user123/../../admin/secret.pdf

Accessing resources belonging to other users at the same privilege level:

# Attack: Spoof referer from any page

1. Hidden Form Fields


<form action="/transfer" method="POST">
    <input type="hidden" name="account" value="123">
    <input type="hidden" name="is_admin" value="false">

    <button>Submit</button>
</form>


POST /transfer
account=456&is_admin=true&amount=10000

2. Disabled Buttons/UI Elements


<button id="admin-btn" disabled>Admin Panel</button>


document.getElementById('admin-btn').disabled = false;
// Or directly calls the API endpoint

// Vulnerable client-side check

    // Hide admin menu

fetch('/api/admin/users', {
    headers: {'Authorization': 'Bearer ' + token}

Bypassing Token-Based Controls

1. JWT Algorithm Confusion

# Server validates JWT using RS256 (asymmetric)
# Attacker changes algorithm to HS256 (symmetric)
# Uses public key as HMAC secret

# Modified JWT header:
{
    "alg": "HS256",  # Changed from RS256
    "typ": "JWT"
}
# Server might accept if not validating algorithm properly

2. JWT None Algorithm

# JWT header:
{
    "alg": "none",
    "typ": "JWT"
}
# Payload:
{
    "user_id": 123,
    "role": "admin"
}
# No signature validation!

Prevention & Mitigation

1. Deny by Default

✅ THE PRIMARY DEFENSE

# ✅ GOOD: Deny by default, explicit allow
@app.route('/admin/dashboard')
@require_role('admin')  # Decorator checks authorization
def admin_dashboard():
    return render_template('admin.html')

# ✅ GOOD: Check ownership for every resource access
@app.route('/document/')
def view_document(doc_id):
    document = Document.query.get(doc_id)
    if not document:
        abort(404)
    
    # Verify current user owns or has access to this document
    if document.owner_id != current_user.id and not current_user.is_admin:
        abort(403)
    
    return render_template('document.html', doc=document)

2. Implement Proper Authorization Checks

# Python/Flask example with role-based access control
from functools import wraps
from flask import abort, session

def require_role(role):
    def decorator(f):
        @wraps(f)
        def decorated_function(*args, **kwargs):
            if not session.get('user_role') == role:
                abort(403)  # Forbidden
            return f(*args, **kwargs)
        return decorated_function
    return decorator

# Usage:
@app.route('/admin/users')
@require_role('admin')
def list_users():
    return User.query.all()

// Java Spring Security example
@RestController
@RequestMapping("/api")
public class UserController {
    
    @GetMapping("/user/{userId}")
    @PreAuthorize("hasRole('ADMIN') or @userSecurity.isOwner(#userId)")
    public User getUser(@PathVariable Long userId) {
        return userService.findById(userId);
    }
}

// Custom security check
@Component
public class UserSecurity {
    public boolean isOwner(Long userId) {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        User currentUser = (User) auth.getPrincipal();
        return currentUser.getId().equals(userId);
    }
}

3. Use Indirect Object References

# ❌ BAD: Direct database IDs exposed
GET /api/document/12345

# ✅ GOOD: Use unpredictable tokens or map to user context
import secrets

# Generate unique, unpredictable reference
document.access_token = secrets.token_urlsafe(32)

# Access via token instead of ID
GET /api/document/k7mP9nQ2rT5vW8xY1zA3bC4dE6fG8hJ9

# Or use session-based mapping
session['accessible_documents'] = [1, 5, 7, 12]
# Map index to actual IDs
GET /api/document/0  # Maps to document 1 for this user

4. Attribute-Based Access Control (ABAC)

# Define access policies based on attributes
class AccessPolicy:
    @staticmethod
    def can_view_document(user, document):
        # Owner can always view
        if document.owner_id == user.id:
            return True
        
        # Shared documents
        if user.id in document.shared_with:
            return True
        
        # Admins can view all
        if user.role == 'admin':
            return True
        
        # Department members can view department docs
        if document.department == user.department and document.is_public:
            return True
        
        return False

# Usage:
@app.route('/document/')
def view_document(doc_id):
    document = Document.query.get_or_404(doc_id)
    
    if not AccessPolicy.can_view_document(current_user, document):
        abort(403)
    
    return render_template('document.html', doc=document)

5. Implement Least Privilege

  • User permissions: Grant minimum necessary access
  • API tokens: Scope tokens to specific resources/actions
  • Database accounts: Use read-only accounts where possible
  • Time-limited access: Temporary elevated privileges that expire
# Example: Time-limited admin access
def grant_temporary_admin(user_id, duration_minutes=30):
    expiry = datetime.now() + timedelta(minutes=duration_minutes)
    user = User.query.get(user_id)
    user.temp_admin_until = expiry
    db.session.commit()

def check_admin_access(user):
    if user.role == 'admin':
        return True
    if user.temp_admin_until and user.temp_admin_until > datetime.now():
        return True
    return False

6. Secure JWT Implementation

import jwt
from datetime import datetime, timedelta

# ✅ GOOD: Proper JWT implementation
def create_token(user):
    payload = {
        'user_id': user.id,
        'role': user.role,
        'exp': datetime.utcnow() + timedelta(hours=1),
        'iat': datetime.utcnow()
    }
    # Use strong algorithm and secret
    token = jwt.encode(payload, SECRET_KEY, algorithm='HS256')
    return token

def verify_token(token):
    try:
        # Verify signature and expiration
        payload = jwt.decode(
            token, 
            SECRET_KEY, 
            algorithms=['HS256'],  # Explicitly specify allowed algorithms
            options={'verify_exp': True}
        )
        return payload
    except jwt.ExpiredSignatureError:
        abort(401, 'Token expired')
    except jwt.InvalidTokenError:
        abort(401, 'Invalid token')

7. Regular Access Control Audits

  • Code reviews: Review all authorization logic
  • Automated testing: Test access control for all roles
  • Penetration testing: Regular security assessments
  • Access logs: Monitor and alert on suspicious access patterns

8. Defense in Depth

# Multiple layers of access control
@app.route('/api/admin/delete_user/', methods=['DELETE'])
@require_authentication  # Layer 1: Must be logged in
@require_role('admin')   # Layer 2: Must be admin
@rate_limit('10/minute') # Layer 3: Rate limiting
def delete_user(user_id):
    # Layer 4: Additional business logic checks
    user_to_delete = User.query.get_or_404(user_id)
    
    # Can't delete yourself
    if user_to_delete.id == current_user.id:
        abort(400, "Cannot delete your own account")
    
    # Can't delete super admin
    if user_to_delete.role == 'super_admin':
        abort(403, "Cannot delete super admin")
    
    # Layer 5: Audit logging
    audit_log.record('user_deletion', {
        'deleted_by': current_user.id,
        'deleted_user': user_id,
        'timestamp': datetime.now()
    })
    
    user_to_delete.delete()
    return {'success': True}

Real-World Examples

Notable Breaches and Incidents

1. Facebook Photo Vulnerability (2020) [VERIFY SOURCE]

  • Impact: Private photos of over 6.8 million users exposed
  • Method: IDOR vulnerability in photo API allowed unauthorized access
  • Cause: Insufficient authorization checks on photo retrieval endpoints
  • Data: Private photos that were never posted publicly

2. Strava Fitness Tracker (2018) [VERIFY SOURCE]

  • Impact: Military base locations and patrol routes exposed
  • Method: Broken access control allowed viewing all users' activity heatmaps
  • Cause: Privacy settings not properly enforced in heatmap data
  • Consequence: Revealed sensitive military installations worldwide

3. Parler Social Network (2021) [VERIFY SOURCE]

  • Impact: 70TB of data including private messages and videos
  • Method: Sequential ID enumeration with no access control
  • Cause: Posts could be accessed by incrementing IDs, including deleted content
  • Data: User posts, videos, GPS coordinates, and metadata

4. Peloton API Vulnerability (2021) [VERIFY SOURCE]

  • Impact: Private user data of millions accessible
  • Method: IDOR in API allowed accessing any user's profile data
  • Data: Age, gender, city, weight, workout history
  • Risk: Enabled tracking of high-profile individuals including politicians

5. Instagram Vulnerability (2019) [VERIFY SOURCE]

  • Impact: Account takeover vulnerability
  • Method: Password reset token could be accessed via IDOR
  • Bounty: $30,000 bug bounty reward
  • Fix: Improved authorization on password reset endpoints

6. Shopify Admin Access (2020) [VERIFY SOURCE]

  • Impact: Potential unauthorized access to merchant stores
  • Method: Broken access control in staff permissions
  • Bounty: $25,000 bug bounty
  • Cause: Insufficient validation of permission scope

Common Vulnerable Scenarios

  • E-commerce platforms: Viewing other customers' orders and payment information
